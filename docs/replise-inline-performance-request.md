# 修正依頼：大量の stdout / stderr でインライン出力が編集をブロックする

対象は `lua/replise/inline.lua`。Julia の起動や実行そのものではなく、実行結果を Neovim のインラインペインに反映する経路を軽くしたいです。

## 再現と観測

Windows / Neovim 0.12.5、`style = "rails", width = "full", max_height = 12, max_lines = 1000`。同じソースバッファでペインを開き、`inline.append(buf, "julia stdout line 12345678\n", "stdout")` を640回呼んだ場合と、同じ文字列を640回分連結して1回だけ渡した場合を比較しました。各条件でペインを作り直しています。

| 初期状態 | 1行ずつ640回 | 640行まとめて1回 |
|---|---:|---:|
| 空のペイン | 133 ms | 1.7 ms |
| 既に1,000行を保持 | 551 ms | 2.4 ms |

これは `append` 呼び出しの合計時間で、Julia の実行時間や端末の描画時間は含みません。現状ではチャンクごとにバッファ更新、`sync`、末尾追従が走ります。上限超過後は幅の計算のために保持行を毎回読み直します。

## お願いしたい変更

- 同一ペインに短時間で届く出力をまとめ、画面反映・レイアウト・末尾追従を1イベントループ周期または1フレームに高々1回にしてください。単発の短い出力まで目立って遅延させないでください。
- `width = "full"` など本文の最大幅がレイアウトに影響しないモードでは、行幅計測と全ログ再走査を避けてください。自動幅のモードは、最長行の削除・上書き後も正しい幅にしてください。
- 混在する stdout / stderr の順序とエラー色、分割された ANSI エスケープ、改行と `\r` による進捗表示、`max_lines`、手動スクロール中の位置を保持してください。完了・中断・失敗時は末尾を取りこぼさず、clear・再実行後に古い保留出力が復活しないようにしてください。

## 受け入れ確認

同じ入力をまとめて渡しても分割して渡しても、最終テキスト・色・状態が一致するテストをお願いします。空／上限到達済みの2条件で、変更前後の処理時間と実際の画面反映回数を記録してください。非同期化後は `append` が戻るまででなく、**最後の出力がペインに反映されるまで**測ってください。実機の Julia でも、多量の出力中にキー入力とスクロールが滞らないことを確認できれば十分です。
